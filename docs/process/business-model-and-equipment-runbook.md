# Runbook: бизнес-модель и конфигурации водомата

Дата: 2026-10-11  
Владелец и утверждающий решений: `strebulaev`

## Назначение

Описывает, как воспроизводимо обновить расчетную бизнес-модель пилотной точки и отдельные спецификации конфигураций оборудования. Неизвестные значения остаются `null`/«не найдено» до подтверждения источником. Запуск генераторов не означает согласование закупки, площадки или эксплуатации.

## 1. Изменение бизнес-модели

1. Отредактировать `config/business-model-inputs.json`. Контекст бизнес-модели хранится в `docs/project/business-model.md`; расчетные входы и исполняемый canvas редактируются в JSON-конфигурации.
2. Для каждого фактического числа заполнить `sources` точным источником и типом подтверждения. Сценарные значения явно обозначить как сценарные. Неизвестные оставить `null`; ноль использовать только для подтвержденного отсутствия расхода.
3. Проверить владельца и метод закрытия неизвестных, которые показывает отчет. Финансовый прогноз точки включает только выручку, переменные/прямые постоянные расходы и результат до амортизации, финансирования и налога на прибыль. Это не полный P&L и не чистая прибыль.
4. Пересчитать локальный отчет, диаграмму и JSON:

   ```sh
   python3 pipeline/business_model.py \
     --input config/business-model-inputs.json \
     --output docs/economics/business-model-calculation.md \
     --diagram-output docs/economics/business-model-flow.mermaid \
     --json-output output/business-model-calculation.json
   ```

   Полная модель и JSON содержат использованные входы, статусы стадий, сценарии и открытые вопросы. Не редактировать генерируемые Markdown/Mermaid вручную.

## 2. Изменение спецификаций оборудования

1. Общую матрицу требований обновлять в `docs/hardware/pilot-spec-v1.md`; профили четырех конфигураций — в `config/equipment-specifications.json`.
2. Не назначать модель, BOM, климатические пределы, IP-рейтинг, цену или нормативное соответствие без подтверждения поставщика, условий площадки и применимого источника. Открытые поля должны называть владельца закрытия и метод проверки.
3. Пересобрать четыре отдельных документа:

   ```sh
   python3 pipeline/build_equipment_specs.py
   ```

4. Проверить, что сгенерированные файлы синхронны с конфигурацией и матрицей:

   ```sh
   python3 pipeline/build_equipment_specs.py --check
   ```

   Результаты: `docs/hardware/specifications/in-std-v1.md`, `in-rei-v1.md`, `out-std-v1.md`, `out-rei-v1.md`. Редактировать эти файлы вручную нельзя.

## 3. GitHub Actions

- **Calculate water-vending business model** запускается вручную через `workflow_dispatch` или при push относящихся к расчету файлов. Для ручного запуска основные поля вводятся через форму; дополнительные затраты, CAPEX, стартовая потребность в деньгах, сценарии и источники передаются через `parameters_json`. Вводы workflow являются непроверенными, пока к ним не добавлен источник. Workflow публикует Markdown, Mermaid, JSON с входами/результатами и overrides как артефакт.
- **Build equipment configuration specifications** запускается вручную или при изменении конфигурации, базовой матрицы, генератора или workflow. Он проверяет закоммиченные спецификации командой `--check` и загружает пакет заново созданных четырех спецификаций.
- Если workflow завершился ошибкой синхронизации, запустить соответствующий генератор локально, включить обновленные выходные документы в тот же коммит и повторить workflow.

## 4. Контроль перед коммитом

```sh
python3 pipeline/build_equipment_specs.py --check
git diff --check
git status --short
```

Для бизнес-модели после редактирования конфигурации повторно запустить генератор и убедиться, что `не найдено` соответствует действительно незакрытым данным. Проверить отчет и диаграмму как обычный пользователь: статусы расчета, единицы измерения, сценарные входы, источники и ограничения прогноза должны быть понятны без чтения Python-кода.

## 5. Условия готовности и передачи решения

- Бизнес-модель воспроизводится из конфигурации; источники привязаны к входам; пробелы и внешние гейты видны в отчете; ручной запуск GitHub Actions дает полный пакет артефактов.
- Для каждого профиля спецификации указаны среда, защита, модули, критерий применения, доказательство приемки и ответственный/способ закрытия неизвестного. `--check` проходит для всех четырех документов.
- До появления подтверждений поставщика спецификации — основа RFQ и технической оценки, а не готовая закупочная ведомость. Пилотное и инвестиционное решения принимаются владельцем после закрытия финансовых, площадочных и нормативных гейтов.
