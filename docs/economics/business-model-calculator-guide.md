# Как пользоваться калькулятором экономики точки

Дата: 2026-10-11. Владелец модели и утверждающий: `strebulaev`.

## Финансовый калькулятор

Этот документ описывает только финансовую модель одной точки: расчёт расходов, выручки, unit economics и сценариев. Понятное описание самого бизнеса находится отдельно: [`docs/project/business-model.md`](../project/business-model.md). Параметрический финансовый калькулятор читает `config/business-model-inputs.json` и запускается через `pipeline/business_model.py`.

Этапы финансового pipeline: проверка входов → расчёт выручки и затрат → unit economics и BEP → сценарии и чувствительность, если данных достаточно → публикация отчёта. Юридические, санитарные и площадочные допуски не вычисляются из финансовых входов и проверяются отдельно.

## Ввод параметров

Заполняйте `config/business-model-inputs.json`. Для каждого фактического значения добавьте запись в `sources` с типом подтверждения и точной ссылкой на договор, котировку, чек, журнал измерений или решение. Для вспомогательных разделов формат ключа — `customer_metrics.<поле>`, `market.<поле>`, `projection.<поле>`, `sensitivity.<поле>`; источник отдельного сценария можно записать как `scenarios.downside.volume_lpd` (аналогично для `base` и `upside`). До появления подтверждения оставляйте `null`: генератор показывает «не найдено» и указывает ответственного и способ проверки. В расходах `0` означает подтвержденное отсутствие статьи; неизвестная сумма — `null`.

Суммы задаются в RSD; объемы — в литрах; месячная модель использует `operating_days_month`; коэффициент uptime — доля времени. Для сценариев внесите собственные отличающиеся драйверы в `downside`, `base`, `upside` и обозначьте их в источниках как сценарные входы. Для downside и upside требуется хотя бы один явно введенный драйвер.

Основные параметры:

| Параметр | Единица / смысл | Как получить |
|---|---|---|
| `price_per_5l_rsd` | Цена за 5 л, RSD | Решение владельца или изменение решения |
| `volume_lpd` | Потенциальные продажи, л/день работы | Пилотное измерение или отдельное явно помеченное допущение |
| `uptime_rate` | Доля времени, когда точка доступна | SLA поставщика и журнал работы |
| `cashless_revenue_share` | Доля выручки безналичных продаж | Фискальный отчет |
| `cashless_order_share` | Доля безналичных транзакций | Число транзакций из фискального/платежного отчета; используется для числа наличных заказов |
| `cashless_fee_rate` | Комиссия на безналичную выручку | Договор эквайринга/платежного модуля |
| `effective_sales_tax_rate` | Эффективный расход на выручку только по письменной модели бухгалтера | Сербский бухгалтер; не вводить ставку налога без его подтверждения |
| `water_tariff_rsd_m3`, `sewer_tariff_rsd_m3` | RSD за м³ | Актуальный счет/письменный расчет BVK |
| `sewer_billing_basis` | `intake`, `reject` или `product` — какой объем облагается водоотведением | Письменное подтверждение BVK; до этого `null` |
| `ro_intake_l_per_product_l` | Литры входа на литр готовой воды | Спецификация поставщика и измерение на пилоте |
| `average_order_l` | Средний объем в транзакции | Машинные и фискальные данные |
| `cash_handling_cost_rsd_per_cash_order` | Стоимость наличного заказа | Фактический процесс и тариф инкассации |
| `refund_and_failed_sale_cost_rsd_per_order` | Средняя стоимость возврата/сбоя на транзакцию | Журналы инцидентов и платежей |
| `monthly_fixed_costs.*` | Прямые расходы точки в месяц: аренда, коммунальные услуги, сервис, лаборатория, вода/готовность, поддержка, труд оператора и локальный маркетинг | Договоры, счета и фактические трудозатраты; офисные/сетевые расходы сюда не смешивать |
| `capex_breakdown.*` | Аппарат, доставка/монтаж, подготовка площадки, документы и начальные расходники/пусконаладка | Подтвержденные котировки и смета до готовности точки к эксплуатации |
| `startup_cash_requirements.*` | Депозит, предоплата аренды, разменный фонд наличных и открывающий оборотный резерв; показывается отдельно от CAPEX | Договор площадки, кассовая конфигурация/график инкассации и календарь платежей |
| `site_area_sqm` | Площадь, занимаемая точкой, в м² | Полевое измерение; поле необязательное |

Генератор рассчитывает помесячную выручку, переменные и прямые постоянные расходы, вклад на литр и заказ, contribution margin, операционный результат до амортизации, безубыточность в литрах и заказах, полный CAPEX, первоначальную потребность в деньгах и два срока возврата: CAPEX отдельно и всех первоначальных вложений. При введенной площади считает выручку на м² и аренду/выручку. Дополнительно поддерживаются CAC/LTV, TAM/SAM/SOM, операционный прогноз точки до 36 месяцев и чувствительность результата/окупаемости. Прогноз включает выручку, переменные и прямые постоянные расходы и операционный результат до амортизации, финансирования и налога на прибыль; он не является полным P&L и не показывает чистую прибыль. CAC/LTV и размер рынка рассчитываются только если введены все необходимые входы.

## Запуск расчёта

Локально после редактирования JSON:

```sh
python3 pipeline/business_model.py
```

Полный локальный пакет с машинно-читаемым результатом:

```sh
mkdir -p output/business-model
python3 pipeline/business_model.py \
  --input config/business-model-inputs.json \
  --output output/business-model/report.md \
  --diagram-output output/business-model/model-flow.mmd \
  --json-output output/business-model/result.json
```

Результат записывается в `docs/economics/business-model-calculation.md`. Этот файл генерируется — редактируйте источник и параметры, затем пересчитывайте.

Полная схема формул также записывается в [`business-model-flow.mermaid`](business-model-flow.mermaid) и встроена в отчет как Mermaid. В GitHub она отображается в сводке запуска; JSON-файл артефакта позволяет повторно загрузить те же входы и результаты.

В GitHub Actions выберите workflow **Calculate pilot unit economics** и запустите `workflow_dispatch`. Основные финансовые входы можно ввести в форме. Дополнительное поле `parameters_json` принимает расширенный JSON для CAPEX, стартового разменного/оборотного cash, остальных статей постоянных затрат, сценариев, источников, CAC/LTV, рынка, прогноза и чувствительности. Пустое поле формы сохраняет значение из конфигурации; введенное поле формы имеет приоритет над JSON. Ручные значения workflow помечаются как `workflow_manual_input` и не считаются подтвержденными без ссылки на доказательство. JSON вводится полным объектом параметров, например:

```json
{"inputs":{"volume_lpd":80,"uptime_rate":0.98},"sources":{"volume_lpd":{"type":"scenario_assumption","reference":"идентификатор замера/основание"}}}
```

Это пример формы JSON, а не прогноз или значение для модели. В сводке запуска GitHub Actions показаны вердикт, таблица сценариев и диаграмма. Артефакт `pilot-unit-economics-<run number>` содержит Markdown-отчёт, машинно-читаемый JSON со входами/результатами/неизвестными, отдельный Mermaid-файл, а для ручного запуска — JSON фактически применённых overrides. Workflow пересчитывает результат при изменении входов, скрипта или workflow; запуск не коммитит и не меняет файлы репозитория.

## Ограничения расчёта

- Тариф воды из локальной базы проекта — вторичный источник и требует сверки с BVK. Все переменные тарифы и база канализационного начисления до ответа BVK остаются открытыми.
- Расход воды считается по `ro_intake_l_per_product_l`; канализация отдельно считается по выбранной базе `sewer_billing_basis`.
- Стоимость привлечения и LTV здесь опираются на введённые данные о клиентах, а не на неподтвержденные рыночные ориентиры.
- Параметры сценариев, прогнозный рост, доли рынка и чувствительность — не факты без источника; неопределенные поля оставляются пустыми.
- Положительная безубыточность или окупаемость не закрывает санитарные, регуляторные и локационные условия запуска.
